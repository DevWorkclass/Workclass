## 1. Synthèse

L'architecture est saine (DDD, validation Zod systématique, POST pour les données sensibles, audit log, JWT + bcrypt 12 rounds, helmet, rate-limit). Les points à corriger en priorité concernent **le déploiement derrière proxy** (rate-limit inopérant), **le stockage des PDF sur disque éphémère** (perte de données + URLs mortes), et **deux race conditions** (quota de réservation et double-scan). Aucune vulnérabilité npm n'impacte le runtime de production.

## 2. Sécurité

### S1 🔴 `trust proxy` non configuré
**Fichier** : [`src/app.ts`](../../backend/src/app.ts)
Render (comme Vercel) place l'app derrière un reverse-proxy. Sans `app.set('trust proxy', 1)` :
- `express-rate-limit` clé sur `req.ip` = IP du proxy → **tous les utilisateurs partagent le même compteur** : soit le rate-limit global se déclenche pour tout le monde, soit (avec `X-Forwarded-For` ignoré) il est contournable. express-rate-limit v7 émet d'ailleurs un avertissement `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR`.
- Les IP anonymisées en audit (`anonymizeIp(req.ip)`) enregistrent l'IP du proxy, pas du client.

**Correctif** :
```ts
// app.ts, avant les middlewares
app.set('trust proxy', 1); // 1 hop : Render/Vercel
```

### S2 🟠 Secrets en fallback `dev_secret`
**Fichiers** : [`jwt.service.ts`](../../backend/src/domains/shared/auth/services/jwt.service.ts) (`JWT_SECRET ?? 'dev_secret'`), [`crypto.ts`](../../backend/src/utils/crypto.ts) (`QR_HMAC_SECRET ?? JWT_SECRET ?? 'dev_secret'`), [`env.ts`](../../backend/src/config/env.ts) (secrets en `.optional()`).
Si une variable manque en prod, l'app démarre quand même avec un secret connu publiquement → **JWT/QR forgeables**. Render génère bien ces secrets, mais rien ne garantit le fail-fast.
**Correctif** : rendre `JWT_SECRET`, `REFRESH_TOKEN_SECRET`, `QR_HMAC_SECRET`, `FEEDBACK_TOKEN_SECRET` **obligatoires quand `NODE_ENV==='production'`** (Zod `superRefine`), et supprimer les `?? 'dev_secret'`.

### S3 🟠 Stockage PDF sur disque éphémère + URLs mortes
**Fichiers** : [`scan.service.ts`](../../backend/src/domains/scan/services/scan.service.ts), [`ticket-generator.service.ts`](../../backend/src/domains/tickets/services/ticket-generator.service.ts).
Les PDF sont écrits dans `./uploads` et l'API renvoie `/uploads/tickets/...`. Or :
1. Aucun `express.static('/uploads')` n'est monté → ces URLs renvoient **404**.
2. Le filesystem Render (Docker) est **éphémère** : les fichiers disparaissent au redeploy/scale.
3. Les certificats contiennent des **données personnelles** (nom du participant) écrites en clair sur disque.
**Correctif** : pousser les PDF vers **Supabase Storage** (déjà configuré : `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, bucket `documents`) et renvoyer une URL signée à durée limitée. À défaut en dev, monter `express.static` derrière `authMiddleware`.

### S4 🟡 Swagger exposé en prod
Swagger UI est servi par défaut (`DOCS_ENABLED !== 'false'`). Il cartographie toute la surface d'attaque. **Recommandation** : `DOCS_ENABLED=false` en prod publique, ou protéger `/api/docs` par auth basique. (La variable existe déjà.)

### S5 🟡 Limite de body 10 Mo
[`app.ts`](../../backend/src/app.ts) `express.json({ limit: '10mb' })`. Aucune route n'attend 10 Mo de JSON. Réduire à `100kb` (ou `1mb`) limite la surface d'abus mémoire.

### S6 🔵 Incohérence origine CORS
`app.ts` lit `process.env.FRONTEND_URL`, mais `env.ts` valide `CORS_ORIGIN`. Si seul `CORS_ORIGIN` est défini, le CORS retombe sur `localhost:3000`. Unifier sur `env.CORS_ORIGIN`.

### S7 🔵 Rate-limit non paramétré
Le limiter global hardcode `windowMs: 15min, max: 100` au lieu d'utiliser `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX` (présents dans `env.ts`). Utiliser l'env pour pouvoir ajuster sans redeploy de code.

### Points positifs ✅
- Validation Zod sur **toutes** les entrées ; erreurs Zod → 422 sans fuite en prod.
- Messages de login génériques (pas d'énumération d'emails) + rate-limit dédié 10/15min.
- bcrypt 12 rounds ; `passwordHash` jamais sérialisé (sélection explicite `publicSelect`).
- Garde-fous anti-escalade testés (création/modif super_admin, octroi `users:manage`).
- `requirePermission` relit les permissions + `isActive` en base → révocation immédiate.
- helmet actif ; HMAC QR vérifié en temps constant (`timingSafeEqual`) ; IP anonymisées (RGPD).

## 3. Performance & robustesse

### P1 🟠 Race condition sur le quota de réservation
**Fichier** : [`booking.service.ts`](../../backend/src/domains/booking/services/booking.service.ts) — `countActiveForTicketType()` puis `repository.create()`. Sous charge concurrente, N requêtes lisent le même compteur avant insertion → **surbooking** au-delà du quota.
**Correctif** : transaction sérialisée + revérification, ou compteur atomique. Ex. :
```ts
await prisma.$transaction(async (tx) => {
  const count = await tx.booking.count({ where: { ticketTypeId, status: { not: 'cancelled' } } });
  if (count >= quota) throw new ValidationError('Quota epuise');
  return tx.booking.create({ ... });
}, { isolationLevel: 'Serializable' });
```
(ou colonne `sold`/`quota` avec `UPDATE ... WHERE sold < quota` conditionnel).

### P2 🟠 Race condition double-scan
**Fichier** : [`scan.service.ts`](../../backend/src/domains/scan/services/scan.service.ts) `confirmScan` — `findUnique` (check `scannedAt`) puis `update`. Deux scans simultanés du même billet peuvent **tous deux** passer le check.
**Correctif** : update conditionnel atomique :
```ts
const r = await prisma.ticket.updateMany({
  where: { id: ticketId, scannedAt: null },
  data: { scannedAt: new Date(), scannedBy: scannerId },
});
if (r.count === 0) throw new ValidationError('Ticket deja scanne');
```

### P3 🟡 Coût DB de `requirePermission`
Chaque requête admin déclenche un `SELECT` sur `admins`. C'est un **choix assumé** (révocation immédiate des droits). Si la charge admin augmente, mettre en cache (Redis, TTL court ~30 s) le couple `role/permissions/isActive` par `userId`.

### P4 🔵 Écritures fichiers synchrones
`fs.writeFileSync` (scan + tickets) bloque l'event loop le temps d'écrire le PDF. Migrer vers `fs/promises.writeFile` (ou, mieux, l'upload Storage de S3) supprime le blocage. Lié à S3.

### Points positifs ✅
- Listings paginés : `findMany` + `count` lancés en parallèle (`Promise.all`).
- Index Prisma présents sur les colonnes filtrées (`status`, `role`, `isActive`, `startDate`).
- Pas de N+1 : les relations sont chargées via `include` ciblés.
- Pool Prisma via pgBouncer (`pgbouncer=true&connection_limit=1`) adapté au serverless/conteneur.
